# 协调者的架构判断

改变跨模块契约、状态所有权或持久格式，或审查暴露结构分歧时读本文件。判据用于比较真实方案，不要求每次逐项生成报告。

## 先建立上下文

读项目的架构文档、受影响模块说明与相关决策记录，再追踪真实生产消费者。记录入口、数据流、唯一写入者、失败与取消路径、持久或传输边界；不能只列文件名。设计理由缺记录时查 git、Issue/PR，区分记录支持的理由与推断。

## 从用法和所有权推导结构

先写两三个真实调用场景或用户操作，再推导接口和类型。取消、重试、恢复、多端消费等只选本需求确实涉及的场景。判断调用者是否需要理解内部阶段、协调多次调用或维护同一状态的副本；能由一个 owner 完成的操作由它承担。

主要访问方式必须能从数据结构解释。指出状态由谁写、其他模块如何读或请求修改；说明非法状态由类型禁止还是在物理边界校验。共享写入优先消除，确实必须共享时再明确串行机制。对可重试或持久操作判断重复执行、中途失败与恢复的结果。

## 比较候选

有结构性选择时，可委派两种不同方案，各用独立输出目录或 worktree。简报给相同需求、约束和消费者证据，不给预设获胜方案；先确定评分依据，再读取结果。局部确定性修改不做候选竞赛。

优先比较：不变量是否成立、调用者负担、接口隐藏的复杂度、写入所有权、与现有架构的适配、owned code 和未来修改成本。模型不同可以帮助发现盲区，但不可作为独立审批的证明。选一个整体作为基础，仅吸收相容的优点；合成后重新检查同一组使用场景。

## 需要解释或重新设计的信号

出现重复绕路、浅封装、泄漏、时序拆分、同步状态或类型逃生口时，回到真实消费者证据再判断；必要的边界适配与物理边界防御不能机械删除。

## 交付给执行者

设计文档保留使用场景、类型与模块责任、数据/状态流、关键不变量、具体备选及取舍、未决风险；写清第一项可验证实现。持久决策写决策记录，审查往返和验证通过列表留交付物。

实现若持续依赖设计未预见的相同绕路，先核实新约束，再修订设计与任务定义，并同步受影响执行者；依赖该契约的任务不能继续按旧简报写代码。
