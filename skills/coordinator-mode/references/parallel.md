# 多 worktree 的协调

协调多个并行任务时读本文件。worktree 数量不是活跃执行者数量，也不是可以同时合入的数量。先完成用户授权的任务，避免为吞吐量不断增加新的在制工作。

## 对齐已有任务与授权

用当前宿主提供的卡片工具和 `git worktree list` 核对任务指针；开发 worktree 以 git 名录与项目约定的 worktree 目录为准，不维护盘上注册表。执行者活性以宿主为准，PR/CI 以代码托管平台为准。名录不是任务内容或完成证明。

用户授权协调既有执行者后才投递消息。派工、回派与暂停都走本 bundle 的 `message_worker`（`sessionId` + `message`），不用别的消息工具猜会话 id——宿主的 `list_agents` / `send_message` / `interrupt_agent` 只认宿主 subagent 体系，本 bundle 的 worker 是普通会话，它们看不到、也投不到。

派活绑定卡槽位，不按「谁空闲」：投递前用查卡工具确认任务挂在哪张卡、槽位上是谁，只派给那张卡的槽位执行者——空闲不等于可派，一会话一时只服务一张卡的一个槽位。`idle` 不等于有人可派：卡槽位与看板信号都看不出「被用户停止」，停用会话状态即 idle。不做事前判断，**投递即探测**：`message_worker` 失败后按错误信息判——报「没有派工记录」说明该会话已撤销（归档会摘掉登记），视作死槽，解除指派后补人；其余错误是普通失败，照常上报，不动槽位。

复用会话承接新任务必须同次改名成卡上任务名，名册与卡上任务不符就是串线信号。改派到另一张卡只调指派指向新卡：它覆盖会话的卡绑定，原卡自动空出；**不要**再对原卡解除指派——会话已不挂原卡，卡绑定不匹配会直接失败。原卡仍 `active` 时要检查是否缺槽位，缺了就补，`done` 卡不补；「摘掉」不算处理，那只是把缺槽位留给活跃卡。

活跃卡（状态为 `active` 且有活要干）必须同时有 dev 与 review 槽位，缺 review 槽位会逼出「借别的卡的审查员」。补槽是派工拿回执后更新卡片的槽位指派；槽位指派不写卡内容，不需要 expectedRevision。

卡片/spec 保留 Issue、设计、执行者、worktree/分支、依赖、写入范围和验收指针；不存在卡片时在该任务已有 Issue/简报中保留，不为单任务再建数据库。dev 的 PR 号在它自己的那一轮里报出，协调者在收到的那一轮里响应：先读该卡 revision，再带 expectedRevision 把 PR 挂进链接——缺 revision 会被要求先读，读到的 revision 过期才报版本冲突。这是同一轮里的两次调用，没有「一次调用既读又写」；「建卡」与「交 PR」之间也没有别的强制动作。需要向用户展示时汇总「任务 / 阶段 / 阻塞或依赖 / PR 与 head / 下一步」，从真源重建，未知字段写未知，不维护第二份人工状态总表。

## 并行什么，串行什么

按验收行为与 owner 划任务，不只按目录。不同文件也可能共享协议、事件语义或状态；这种依赖不能用 worktree 隔离消除。

每个实现任务一个独占 worktree、一个写入负责人。开新任务前核对主线当前门禁；红期间遵守项目约定，先修复已有问题，不传播坏基线。

独立任务可以并行。共享类型、事件或接口由一个底层任务拥有；依赖它的上层可以先调查、设计，实现从底层合入且主线验证后开始。除非用户另有明确安排，不默认建立长 PR 栈。

修改范围改变时重查变更范围与语义重叠。冲突回到 owner 和契约裁决，不能只解决文本冲突就声明安全。

先利用现有执行者与其 worktree，续跑时补齐新指令和当前产物；只有上下文错误或产物无法可信恢复时再换新执行者。审查使用另一执行者，必要时协调者亲自复查关键事实。

约十个 worktree 可以同时存在于讨论、实现、审查、CI 与待合入阶段。按真实资源调节活跃数：审查/CI 队列积压、共享机器上的测试争用或关键依赖未完成时，优先消化队列，再开新实现。默认开发命令会清理已有开发进程，并使用固定端口与共享配置，不能视为隔离实例；真实应用驱动按项目的隔离约定串行。源码调查、单测、静态门禁在各自工作区与输出隔离后可并行。

## 发出可独立执行的简报

简报按任务大小缩放，小任务可以一段写完，但必须交代下列信息；已在卡片/spec、PR 或文件中的正文按 [协调者传话纪律](../playbooks/program.md#输出与传话纪律)传指针，不复制到派单：

```text
目标与验收：用户可观察的行为；什么算完成；不做什么。
上下文：Issue、设计、相关决策记录；已知事实与未决问题。
所有权：执行者、独占 worktree/分支、允许写入范围。
禁止：不得触碰的路径、共享实例及外部动作。
依赖：上游任务及当前提交；何时可以开始；共享契约 owner。
证据：对应最小验证命令；需要复现、截图或回放的行为。
时限：停止/放弃条件、等待上限与超时后的处理；无时限明确写无。
授权：实施与修复范围；approve/merge 是否获准。审查发布按项目规则收尾，不另索许可。
回报：实际文件/提交与 PR、head、验证及缺口、偏离设计与阻塞。
```

设计调查只要候选与理由，审查只要发现与证据，不把「发现问题」默认扩成实施授权。委派测量时另给采样方法与精确提交，避免每个执行者测到不同对象。派前核对范围、验收、禁止项和停止条件；缺少执行必需信息先补齐，简报可用真源指针承载，不为字段形式重复派单。

## 接收结果与审查收敛

收到完成通知后读产出再裁决，无需反复询问运行中的执行者。查询只为诊断异常或核对新事实，不靠频繁消息充当心跳。需要固定时间巡检时遵守当前宿主的 automation 机制，不在技能里假定某个调度命令存在。

核对 PR 基线与 head、实际 diff、验收与证据适用范围，缺失或无法运行的验证标为缺口。将实现状态、行为验收、审查和 CI 分开判断；worker 的 PASS 不覆盖任何一项。

用户授权审查后，审查者获得精确基线与 head、需求意图及需要保留的不变量。协调者逐条核实、去重、裁决，不以多数票判真伪，也不要求每轮更换模型。回派包含可复现问题、影响和验收；同一根因重复出现时检查设计与简报，不无限重复同一提示。

补提交、retarget 或合入新基线后，旧证据仍只属于旧提交；根据实际差异重验受影响行为和审查范围，当前 PR required checks 必须重新核对。BLOCKED 是缺口，不能作为通过。

## 用户回来时的进展说明

用户要求追进度或恢复全貌时，以上一条真实用户消息为起点，通知与执行者结果不算用户消息。只读核对本任务涉及的实际 PR/CI/执行者，不为报告启动应用、改代码或发布。旧待决项仍保留，未知写未知；修正数字前查来源。

先说有几项需要用户决定，再按用户熟悉的任务名称解释发生了什么、对用户的影响和目前状态；没有变化且无待决项就直接说明。简短但不截断必要内容，不贴状态名录、哈希和命令清单，细节给真源指针。复用真实截图/视频，依赖或选择难懂时用小图，不造图补证据，不在文字和图里重复。

行动项只含用户必须作的选择、权限或不可逆决定，每项交代建议及理由、前置条件、收益/代价和不回应的影响。Agent 授权内能继续做的事列剩余工作，不转交用户；不凭空制造选择，不把待决任务标完成。跨任务汇总限已授权范围，仍遵守 [协调者简报](../playbooks/program.md#输出与传话纪律)。

## 合入与清理

待合入材料包括当前 head 的验收、审查、required checks、上游依赖和残留风险；未获用户明确授权不 approve、不 merge、不设置自动合并。批量合入仅覆盖明确授权的 PR，按依赖次序与项目合入窗口执行。

合入后以最新主线 push run 的门禁终态核对组合状态；红立即处理，绿后再开启下一批。清理条件与命令完全遵守项目约定，不因卡片显示完成、PR merged 或磁盘紧张提前删除重试载体。
