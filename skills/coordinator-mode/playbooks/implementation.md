# 实现、缺陷与重构

共用前提：已有验收、设计/Issue、独占 worktree 和明确写入 owner；委派简报见 [并行协作](../references/parallel.md)。行为驱动、fixture、永久回归与覆盖率以项目约定为准，验证范围按项目既有门禁选择，结构判断按 [专项能力方法](../SKILL.md#按问题调用专项能力)。

本 playbook 可由普通单会话或 dev worker 直接使用，不要求加载协调者入口、建卡或启动派工。共同工程要求相同；worker 的任务来源、交接对象与阶段归属由宿主身份和派单确定，普通会话直接向用户交付。

## Feature

先追现有用户入口与消费者；改变 owner 或边界时先做架构比较。开工前确认阻塞首步、可独立工作流、共享状态和最小安全分解，依赖未合入的任务可以调查而不抢写契约。按可观察单元实现，逐单元验证，再验整体用户路径；临时工具或自报完成不能代替真实行为。同步消费者文档、必要回放与 GUI 证据，最后走交付流程。

## Bug fix

保留原触发输入与环境，列可反证假设，用最便宜探针排除；先复现正确失败再改原因。重大缺陷必须永久回归与决策记录，不能用 flaky 失败充当复现。相同输入、原路径证明修复，再检查邻近合法行为；审视完整 fixture 和测试安排是否能抓住该缺陷，必要时暂时引入缺陷确认测试拒绝它，随后恢复。重复绕路先重查前提。交付机制、触发、修复与证据，不用「加 retry 后不报错」代替因果解释。

## Refactoring

先固定不改变的消费者行为，再定义结构收益：少 owner、少 owned code、隐藏易变决定或降低阅读负担。核对全体调用者；内部 API 一次更新并删旧入口，不做无消费者兼容层。每个结构单元验契约，合成后重验；typecheck 不能证明行为等价。新 feature 不混进结构调整；简化证据与决策记录按项目简化规范。

## 交付与修复

按 [delivery](delivery.md#开-pr)交付产物与证据。修复时自己读取该交付物的审查评论，不等协调者转述；逐条核实，采纳的修复后回复处置，不采纳给证据与理由，不静默跳过。继续使用本次独占 worktree 和可恢复的会话，不因一轮修复另建任务。

交接按宿主身份：worker 最终回复只给结论、产物与 head 指针、关键验证、缺口和待决/阻塞，详细材料留原报告或交付物；普通会话向用户报告。开发完成不代整卡验收，不标整卡 done；有卡时回交协调者按验收判断。approve/merge 遵守项目约定。
