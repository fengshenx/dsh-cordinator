# 项目作用域与角色槽位

**状态**：implemented（P3，2026-10-23）
**范围**：`src/host/slots/`、`src/host/cards/store.js`、`src/host/tools/projects.js`、`src/client/project-switcher*.js`、`skills/coordinator-mode/SKILL.md`

## 背景

P0–P2 已交付协议层、初始化工具、派工唤醒、卡片存储与右栏看板。剩下两件 Telov 有、dsh 没有的东西：**项目作用域**与**角色槽位**。

Telov 的项目是持久实体（`candyapp/packages/shared/src/types/project.ts:15`：`id`/`name`/`directory`/`coordinatorSessionId?`），一个项目对应一个协调者会话、一组卡片、一份槽位配置；切项目即切协调者会话。角色槽位是项目根的 `SLOTS.md`（`candyapp/apps/electron/src/main/lib/project/slot-templates.ts:25`），按 `## <槽位名>` 分节，正文作为 role_context 注入会话；每次 turn 构造时重读文件，无 watcher。

dsh 侧要先回答「项目」对应什么。`profile`（`$DSH_HOME/profiles/<name>`）是插件组合层，不含「项目 = 一套插件组合 + 一个协调者」的语义。真正对应的是 `workspace` 家族——`ctx.workspaceRegistry`，「提供命名且有序的项目，并按目录归组在其中运行的会话」（`deepseek-harness/packages/workspace/workspace/README.zh.md:27`），几乎就是 Telov 的项目。

但 `workspace` 只在 web-app bundle 挂载（`packages/bundle/web-app/cordis.patch.yml:91`），且它不会向模型公开工具、提示词或会话事件（`packages/workspace/README.zh.md:12`）。第三方 bundle 拿不到它——P1 已经踩过同类坑：`sessionController` 只挂 web-app bundle，声明成必需 inject 会让 headless 等 profile 整个插件挂起（见[客户端半边的发现与构建约束](2026-10-23-客户端半边的发现与构建约束.md)）。

## 决策

**项目 = 目录，不建项目实体**。项目标识是目录绝对路径；项目列表是「有会话的目录集合」，不落盘、不建库。被否的两个备选：自建项目实体（与 workspace 重复造概念，且 dsh 已覆盖命名与排序）；把 `workspaceRegistry` 写进 `inject`（非 web profile 缺服务会让整个插件挂起）。

**项目列表取自持久化会话语料，不是 live session**。`ctx.sessions.list()` 只返回进程内 live session（`packages/core/session/src/index.ts:1359`），进程重启后未加载的历史会话不在其中——昨天的项目今天会从列表消失。稳定的源是 `ctx.sessionQuery.listSessions()`（`packages/session-query/session-query/src/index.ts:174`），它合并持久化记录与 live session（live 优先，`packages/session-query/session-query/src/corpus.ts:62`），每条记录带 `header.cwd`（`packages/session-query/session-query/src/types.ts:27-29`）。`ctx.sessionQuery` 由 sqlite 引擎提供（`packages/session-query/session-query-sqlite/src/index.ts:202`），base bundle 已挂载（`packages/bundle/base/cordis.patch.yml:157-158`）。因此项目列表按 `header.cwd` 去重后不随进程重启漂移。

由此定下 `list_projects` 工具的形态：它是**异步**的（`listSessions()` 返回 promise），且走 `ctx.get('sessionQuery')` 惰性获取——`sessionQuery` 虽在 base 挂载，但 sqlite 引擎可能被部署替换或缺席，与 `sessionController` 同属「不能声明为必需 inject」的一类。缺失时工具降级为只列 live session，并说明列表不完整。

**同一目录的「当前协调者」靠协议层软约定唯一化**。项目 = 目录丢掉了 Telov `coordinatorSessionId` 提供的硬唯一性：同一目录可以同时存在历史协调者会话、worker 子会话与 fork，会话目录本身不区分身份。协议层约定「一个目录同一时刻至多一个活跃协调者会话，由协调者在建立或接手时自觉维护」——不做运行时校验。相应地，「切到某项目」的目标是**该目录下约定的活跃协调者会话**；无法从目录反查出唯一答案时，切换动作由用户从该目录的会话列表中指定。

**切项目 = 切会话**。`SessionHeader.cwd` 是 readonly，创建时定死（`packages/core/session/src/types.ts:106`），会话改不了目录；`session.create` 接受 `workspaceId` 或 `cwd` 二选一（`packages/api/session-controller/src/commands.ts:112-124`）。所以切换只能是导航到/创建另一个 cwd 的会话——这与 Telov「切项目 = 切协调者会话」本来就是同一件事，不是降级。

**槽位注入落点是 `ctx.systemPrompt.context()` 注册的运行时上下文，不是 section**。这是实现期实测修订的结论，原方案（`section()` 的函数式 text）不成立。

原方案错在**混淆了两种提示词载体的生效时机**。`section()` 注册的段进的是**系统提示词消息**，而那条消息是会话级固定的：它只在请求序列重启时重新投影（`packages/core/agent-loop/src/agent.ts:407-425` 的 `systemPrompt.project`，`startsSeries` 为假时不追加新消息）。槽位配置改了、工具没变、请求序列没重启，那条消息就不会重写——「变更在下一轮 turn 生效」落空。实测证据：会话建立后再注册进去的段，在后续请求的系统提示词里始终不出现。

运行时上下文（`assembly.contexts`）没有这个限制：provider 每轮组装时重新求值（`packages/core/system-prompt/src/index.ts:582-602` 的 `refreshContext`），快照有变化才作为一条 user 消息追加（`packages/core/agent-loop/src/runtime-context.ts:152-163`）。「槽位配置变更在下一轮 turn 生效」因此是结构性的，不需要 watcher，也与 Telov「每次 turn 构造时读文件」一致。

`AssembleContext` 带 `agent`（`packages/core/agent/src/runtime-types.ts:18-22`，由 `assembleContextFor` 填入，`packages/core/agent/src/dispatch.ts:174`），所以**一个全局 provider 即可按 agent 分流**，不必做 per-agent 注册。`systemPrompt` 服务由 base bundle 挂载（`packages/bundle/base/cordis.patch.yml:505`），sdk-minimal 自带一行（`packages/bundle/sdk-minimal/cordis.patch.yml:114`），headless 则在 base 层之上覆盖该行的 config（`packages/bundle/headless/cordis.patch.yml:9-12`）——三处都表明该服务在全部官方 bundle 存在，可安全进 `inject`。

**上下文必须注册成 provider，不能只在组装事件里临时追加**。`refreshContext` 按注册表重新求值上下文，注册表里没有的临时项在运行时被抑制的场景下会被丢弃（`packages/core/system-prompt/src/index.ts:591`：`if (suppressed && provider?.required !== true) continue`）。声明 `required` 则让它在可选运行时被关掉时仍然保留。

**槽位配置放 `<项目目录>/SLOTS.md`**，与 Telov 同构，零新增存储域；只读不写，用户与协调者用 Write/Edit 维护。

**槽位绑定的真源是卡片 store 的 `slots` 字段**。P2 已实现该字段与改卡通路但未接线（见[卡片存储与编号作用域](2026-10-23-卡片存储与编号作用域.md)），P3 只补 `sessionId → 角色名` 的反查。反查表在 host 侧是内存索引：`text` 是同步函数，不能在里面 `await`，而落盘的卡片库是异步读的。索引只在读侧使用，卡片库仍是真源，进程启动时重建即收敛。

**索引在运行时随改卡同步更新**。`update_card` 改 `slots` 成功后，工具层必须同步更新内存索引，否则「槽位改绑后下一轮 turn 仍注入旧角色」——恰好破坏「变更在下一轮生效」这条结构性保证。索引只服务于读侧，落后一版只会让注入滞后一轮；崩溃窗口由启动时重建兜底。

**槽位不授予工具权限**。dsh 没有角色权限模型，工具可见性只由 `ctx.tools` 注册与 scope 决定；槽位只贡献一段 system prompt 文本，不注册任何工具、不改工具可见性——这是结构性保证，不靠运行时校验。协议层同步保留免责表述，避免协调者误以为槽位授予了权限。

**client 侧的会话导航走惰性获取 + 降级**。`ctx.uiWorkspace.openSession()` 由 web-app bundle 的 `@deepseek-ai/dsh-client-ui-workspace` 提供（`packages/bundle/web-app/cordis.patch.yml:361`），第三方 bundle 不把它写进 `inject`，改用 `ctx.get('uiWorkspace')` 惰性获取，缺失时降级为「复制项目路径 + 提示用户在目标目录新建会话」。这与 P1 对 `sessionController` 的处理是同一条纪律。

## 边界

- **卡片不按项目分区，编号仍全局递增**。按项目编号要迁移存量卡片的编号作用域（已在卡片存储 note 里记为已知代价），P3 不做。因此跨项目的卡片在同一个库里混列，`@#n` 引用在跨项目场景下会歧义。
- **不建项目实体**，故没有项目名、排序与归档。项目名只能取目录 basename（dsh 的 `displayTitleOf` 已是此策略，`packages/api/session-controller/src/client/sessions/service.ts:119`）。
- **`spawn_worker` 的子会话默认继承父会话目录**。`SubagentStartRequest.cwd` 省略时继承父会话当前目录（`packages/subagent/subagent/src/types.ts:137`），provider 收到的 `ResolvedSubagentStartRequest.cwd` 是必填的绝对路径、「captured from the parent or explicit request」（`:186-188`）。故 worker 的 `SessionHeader.cwd` 就是项目目录，worker 侧槽位注入成立；只有将来显式覆盖 cwd 时才需要另行传递项目标识。
- **同目录多会话时「该项目的协调者」没有运行时唯一解**。目录不区分会话身份，约定靠协议层自觉维护（见决策段）。歧义无法从目录反查消除，只能由用户在会话列表中指定。
- **槽位变更对在途 turn 不生效**。dsh 在 step 前组装提示词，组装结果对该 step 固定；生效边界是下一个模型请求。
- **槽位只对绑定了卡片槽位的会话生效**。未绑定或绑定角色在 `SLOTS.md` 中不存在时，注入为空串，该上下文不贡献内容（`renderContextSections` 过滤空文本，`packages/core/system-prompt/src/index.ts:330-336`），非本 bundle 的会话零影响。
- **运行时上下文是增量快照，不是每轮全量重发**。宿主只在快照文本变化时追加新消息（`packages/core/agent-loop/src/runtime-context.ts:155`）。槽位正文没变的那一轮不会重复注入——模型已经知道自己的角色，不必重复消耗上下文。

## 证据

机制结论来自 dsh 0.2.1-rc.2 源码阅读，引用位置逐条标在正文；注入落点与生效时机两条另经实现期实测修订，见上文决策段。

已实测的边界：

- **注入落在运行时上下文而非系统提示词**。用 mock LLM 捕获请求体：系统提示词消息在会话建立后不再随槽位配置变化重写，运行时上下文消息随 `SLOTS.md` 正文改写而更新。
- **槽位不授予工具权限**。注入前后两轮请求的工具定义数组逐字节一致（32 个工具，含本 bundle 注册的 7 个）。这是结构性结论：注入只写提示词文本，不碰 `ctx.tools`。
- **注入不改变其他会话**。未绑定槽位的会话拿不到该上下文。
- **项目切换的 host 侧**：`switch_project` 按目录查出该目录约定的协调者会话并返回，目录没有会话时如实说明需要在目标目录新建。
- **client 侧切换**已验证：项目切换器列出全部有会话的目录、当前项目标注「当前」；点击目标项目后主视图切到该目录的协调者会话。自动化环境里页面合成点击整体无效（连宿主自带的面板关闭按钮也不响应），这一步由人工点击完成——不是本 bundle 的代码问题。
- **仓库外的插件改动进不了 bundle 产物**：client 产物由 web 进程启动时打包，改动后必须重建产物并重启 web 进程，刷新页面才会生效。
